# Ogabassey × Yield / BrilStash catalogue pilot

Review draft · 18 November 2026 · No endpoint, publication, production data changes, or partner communication performed.

## Contract and evidence

The task supplies the authenticated [vendor developer guide](https://portal.brilstash.com/vendor/developer) contract: `GET /partners/yield/brilpay/products`; JSON array; stable `external_id`, `product_url`, `title`, plain-text `description` including condition, specifications, box contents and warranty, exact partner category label, `price_naira`, numeric `stock_quantity`, 1–10 HTTPS `images: [{url}]`, optional `brand` and `model_number`. Support `page`, `limit` (example 100), `min_price`, `x-total-pages`, `x-total-count`, optional bearer authorization, and a 10-second budget per page. BrilStash pulls nightly at 23:59 Africa/Lagos (22:59 UTC), approves new products, automatically updates approved listings, expects zero quantity for sold-out listings, and takes absent listings off sale. Orders are described in its dashboard.

The guide could not be independently reopened: web access failed and the browser connector reported its profile was already in use. The supplied contract is the planning input, not a newly verified partner response. Exact category values, the category property's spelling (samples provisionally use `category`), maximum limit, price precision, and pull transaction behavior require authenticated confirmation. No category labels or partner capabilities are inferred from Google taxonomy.

## Offer identity, facts and categories

Persist one mapping keyed by installation + immutable sellable source reference: `product:<uuid>`, `variant:<uuid>` or `offer:<uuid>`. Mint an opaque immutable partner listing ID once; do not derive it from title, price, SKU text, slug or category. Retain retired IDs. Sample readable IDs are illustrative, not production database identities. A source model migration must preserve the mapped identity only when a reviewed mapping proves it represents the same sellable item; otherwise retire the old listing and create a new one for approval. An unchanged source UUID does not prove the sellable item stayed the same. Alongside each identity, record its parent, exact condition and normalized purchasable attributes such as storage and colour. Exclude display copy, prices, stock and category from that identity comparison. Changes to identity-bearing fields on the same source require an operator decision. A correction that represents the same sellable item can preserve its ID after review. Repurposing a source requires retiring the old ID and allocating a new one. Keep the history and permit only one active binding per source. Until that decision is applied, block promotion and fail reads of affected generations whose live source no longer matches the reviewed identity.

For SKU matrix products emit only public sellable variants with their condition, actual attributes, effective sale price (`price_override ?? variant.price ?? product.price` only where that schema/model supports it), approved availability and matching images. For legacy products, use the source the storefront and checkout actually select for each condition. The category PDP projection in `apps/web/src/app/(storefront)/[slug]/(catalog)/(pdp)/[category]/[productSlug]/lcp-route-product-projection.ts` removes offer rows for the parent's normalized condition. Include the real primary sellable row when the parent supplies that condition, and include alternate selectable offers once each. An aggregate family row or a redundant primary-condition offer must never be emitted. If two source rows collapse to one storefront selection, or opening the URL changes the selected condition or price, reject the ambiguous candidate until the exact sellable source is verified. Missing/ambiguous condition is a rejection, not an assumed New condition.

`price_naira` is numeric NGN major units; do not send CrossRem's kobo values or compare-at price. Require finite positive values, NGN merchant currency and an explicit partner-approved decimal/rounding policy. No financing markup, delivery fee or protection charge without an agreed price contract.

A reviewed mapping maps merchant category IDs to exact copied BrilStash labels with a mapping version and review date. Multiple category memberships require one explicit chosen mapping; no guessing from the first join or free text. The proposed families are Phones, Computers, Tablets and Accessories, but these are planning names, not asserted partner labels. An unmapped new record is excluded with a diagnostic; a previously published record losing required facts blocks promotion instead of silently disappearing.

Record the authoritative inventory source for each approved row. For quantity-tracked stock, use the exact product, variant or offer quantity that checkout decrements. For strict serialized products and variants, use the merchant-scoped public availability count for that sellable reference. Only export condition offers from quantity-managed pools with a finite offer allocation. Baci checkout currently rejects condition-selected offers from serialized pools. The default policy excludes unbounded stock. The storefront summary resolves effective product and variant tracking policies and can use a non-public inventory anchor for a simple product. Use the anchor only as an internal stock lookup, with the simple product as the exported identity. Distinguish a successful count of zero from an unavailable count. Build from one consistent source read and expose no individual unit records. A conflicting zero and positive legacy field must be reconciled, not resolved by the shared fallback. Quantity-managed products and variants need an explicitly enabled stock-management flag and a known quantity because checkout decrements ordinary stock only with that flag. Unknown, null or untracked inventory is excluded under the default policy. A previously published source that becomes untracked under that policy cannot keep a positive quantity in an active generation. If it is still public, use an operator-approved zero-stock withdrawal and keep the same ID until retirement. Until that replacement is available, fail the pull and use the agreed partner-side pause or takedown. Never use retained facts to publish a private or repurposed item. The served stock quantity is a nightly snapshot. Fail the entire pull if any live authoritative count drops below its published quantity. Until replacement, follow the daytime pause or takedown procedure for stock already imported by BrilStash. BrilStash orders do not reserve stock in Baci under this pilot. Agree a daytime procedure with BrilStash before launch.

An operator may bind a fresh pilot installation with the source-on-demand policy. For its approved public products and variants with stock management explicitly off and no serialized inventory policy, publish 100 units of sourcing capacity per listing. The regular eligibility, immutable snapshot, and pause rules still apply. Tracked counts and approved zero-stock withdrawals override sourcing capacity.

For the pilot, use an installation-scoped, versioned listing facts record keyed to the exact approved source and its reviewed identity. The operator CLI previews and approves plain-text specifications, box contents and warranty terms from a checked product record, packaging or merchant warranty policy that applies to that exact condition. Keep the evidence reference, reviewer and approval timestamp internal. An explicitly verified absence of warranty can be represented only with partner-approved wording. A missing or unapproved value cannot become a warranty claim. The builder uses the approved facts for those sections and derives the condition label from the reviewed identity. Do not inherit warranty or box contents from sibling conditions or use generic product copy to fill a gap. Read the approved facts revision with the rest of the source data, record per-row revision IDs in the generation, and check them at promotion. An intervening approval or withdrawal invalidates the candidate. An urgent correction to a published warranty or packaging claim uses the existing suspension and replacement process.

## Consistent pagination and failure protocol

Serve a complete, prebuilt immutable generation, ordered by `external_id` ascending. Apply `min_price` inclusively before counting and slicing. Proposed query contract: `page` integer >= 1; `limit` integer 1–100, default 100; `min_price` finite nonnegative NGN, default 0. Confirm these bounds with the partner. Return 400 for malformed/duplicate/unknown parameters, 401 for missing/invalid configured key, and safe no-store 503 for unavailable/incomplete generations. Unknown host/installation cannot select another tenant. Beyond-last page returns `[]` with accurate totals; a legitimate empty result uses zero pages/count, subject to partner confirmation. Never return a successful empty array for DB failure. The authoritative nightly sync uses the full unfiltered assortment. A positive `min_price` is a filtered view and must never take listings off sale by absence from that view. Verify that BrilStash either omits the filter for authoritative imports or scopes reconciliation so filtered-out listings outside that view are untouched. Test a previously approved, in-stock listing whose price drops below the filter threshold in a sandbox pull.

Build daily at 22:00 Lagos (21:00 UTC), before the 23:59 pull, using a consistent DB snapshot or an existing verified catalogue generation; separate uncontrolled live queries are insufficient. Build failure leaves the current generation pointer unchanged and alerts the operator. Publish atomically only after validating all existing listings, counts, IDs, mappings, URLs and images. Retain previous complete generations for recovery. No silent 10,000-product truncation or source-batch omission. Capture the expected active generation ID and the catalogue revision in the same read as the source data. Stage a complete validated candidate with those values and its original source-read timestamp. Staging does not change the active generation or serving state. The catalogue revision changes on approvals, retirement, eligibility control changes and urgent suspension. Ordinary drain closure, evidence recording and abort use a separate closure revision, so the validated candidate can survive those steps. Promotion checks the candidate's expected active ID and catalogue revision plus its current eligibility and freshness under the installation lock. In drain mode it also verifies that the current closure and its evidence match the expected old generation and closure revision.
