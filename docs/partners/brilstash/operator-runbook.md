# BrilStash pilot operator runbook

Use the [pilot specification](2026-11-18-catalogue-pilot.md) for the product contract and qualification steps. The [pilot fixtures](pilot/) contain synthetic data. Partner communications, hosted sandbox publication, registration, and live rollout require separate authorization. Production scheduling remains disabled.

## Commands and credentials

The commands take a local JSON file. Builder and operator commands use an ordinary Supabase Auth access token in `BRILSTASH_TOOL_ACCESS_TOKEN` and the project’s public key in `NEXT_PUBLIC_SUPABASE_ANON_KEY`. For a hosted target, supply an `sb_publishable_` key and set `BRILSTASH_TOOL_TARGET=hosted`, the exact `NEXT_PUBLIC_SUPABASE_URL`, and its `BRILSTASH_SUPABASE_PROJECT_REF`. For a disposable local API, set `BRILSTASH_TOOL_TARGET=local` and use a numeric loopback URL with an explicit port. A legacy anon JWT is accepted only for that loopback target. Use separate credentials and projects for sandbox and live. Keep secrets out of JSON files, command arguments, shell history, and review evidence.

```sh
pnpm --filter @baci/web brilstash:manage inspect.json
pnpm --filter @baci/web brilstash:build stage.json --apply
pnpm --filter @baci/web brilstash:manage action.json --apply
pnpm --filter @baci/web brilstash:verify probe.json --apply
```

Operator inputs have the shape `{"action":"inspect-candidate","args":{"p_installation_id":"<uuid>","p_candidate_id":"<uuid>"}}`. The [operator schema](../../../apps/web/src/schemas/brilstash-operator.ts) lists the actions and their exact arguments. `--apply` is needed for writes. For a lost response, inspect persisted state before repeating an operation.

For an approved source-on-demand pilot, use `bind-source-on-demand` with the merchant ID and the canonical fresh BrilStash installation identity. This opts that installation into advertising up to 100 units per approved untracked listing backed by merchant sourcing. Tracked quantities and reviewed zero-stock withdrawals take precedence. For sourcing interruptions, use the existing suspension and withdrawal procedures.

Use a separate, installation-scoped builder account. Supply the installation ID, stable candidate UUID, reviewed merchant slug, and product hostname to the builder. Use an active domain registered to that merchant or its Baci storefront subdomain. The builder normalizes an explicit HTTPS default port to the same origin. Staging binds the title, brand, description and exact PDP selection to the approved source. The pilot omits the optional vendor model number until an authoritative listing-level source is available. The command stages a candidate. Inspect the exact candidate and its digest, then record the operator's approval before first activation or handoff of a replacement. Before first activation, record the confirmed drain and retry bounds with `configure-drain`. Within the dated Lagos activation window, recheck the partner installation while both import controls are disabled and record the resulting evidence immediately. Activate the exact approved seven-listing candidate before five minutes have elapsed since evidence was recorded. If the evidence expires, repeat the partner readback and record a new receipt. Inspect the resulting active generation and activation timestamp.

If an approved listing becomes invisible or its URL, price or other required data becomes unusable, staging returns `incomplete_assortment` or `unapproved_removal` and the builder reports the missing approved listing IDs. Correct the data, apply a reviewed source remap, or explicitly retire the listing before staging a replacement. Leave the ID in the approved assortment until that decision is recorded. Verified image URLs must use HTTPS with a DNS hostname. Use percent encoding for non-ASCII URL characters and re-verify invalid URLs in the source manifest. Staging checks the complete verified image sequence in manifest order and preserves each emitted URL verbatim. The first occurrence wins when URLs differ only in scheme or hostname case, port spelling, an explicit HTTPS default port, a trailing DNS dot, or an implicit root path. The payload contains at most ten images.

A candidate staged before the display revalidation migration must be staged again and approved under a new candidate ID. A storefront name, slug or brand change after staging blocks activation or promotion. If authoritative stock drops below what the serving snapshot advertises, the feed returns 503 and the operator follows the partner pause or takedown procedure.

Production applies the reader migration and its history row in one transaction. It revokes the temporary schema `CREATE` grant used to transfer the reader function in that transaction. The BrilStash privilege suite checks the effective schema grants after replay.

## Verify and hand off

The Host header is client-supplied routing input for the Next.js route. The hostname and deployment checks select the configured ingress. Routing reserves case and trailing-slash variants of the exact feed path so they cannot fall through to storefront slug handling. Generic API paths still use the lowercase `/api` prefix. The database RPC requires a short-lived signature from the configured feed deployment and independently authenticates the installation bearer. It also checks admission, freshness and source eligibility on every request. Direct PostgREST calls without the deployment signature are rejected before the catalogue lookup. If the database rejects the deployment proof, the feed reports a 503 and logs the request ID. A 401 indicates failed partner bearer authentication. The route accepts any casing of the Bearer scheme and sends the unchanged token to the database.

Set `BRILSTASH_FEED_HOST` to the approved bare lowercase DNS hostname without a port or trailing dot. Configure ingress to send that hostname for the HTTPS feed. The feed also accepts the same Host with an explicit default port of 443. Use the same hostname in the URL saved in BrilStash. Supply the intended partner bearer via `BRILSTASH_FEED_BEARER`. The probe input includes `installationId`, `expectedGenerationId`, and `expectedPayloadDigest`. The probe checks the exact HTTPS URL with `page=1&limit=100&min_price=0`, rejects redirects, compares all projected values and array order, and samples serving state on both sides of the request. The live feed accepts unfiltered page 1 with any limit from 7 through 100 so that the full pilot fits on one page. The handoff probe always uses 100. Use `--apply` to persist the successful receipt and obtain its `probeId`. Use `check-handoff` with that ID before a registration operation.

Configure a separate 32-byte random key encoded as lowercase hexadecimal in each deployment’s server-only `BRILSTASH_FEED_INGRESS_KEY` and store the matching value as the unique `brilstash_feed_ingress_key` entry in that project’s Supabase Vault. Keep this key separate from the partner bearer. Configure the shared Upstash Redis rate limiter in both feed deployments. On the configured host, the feed allows 30 well-formed requests per minute per trusted client IP before calling the database. Malformed credentials or query parameters have a separate 15-request budget. Callers behind the same NAT share these budgets, and partner key rotation leaves the IP counters intact. Live and sandbox requests require a trusted client IP. Verify that each ingress supplies it during qualification. Requests without a trusted IP are rejected before accessing the rate-limit store. An exhausted budget or unavailable limiter returns 429 with `Retry-After`. Treat the entire pull as failed and retry within the agreed retry window.

The route allows 8 seconds for the database read and the handoff probe allows 10 seconds for the full HTTP request. Use the response's `X-Request-Id` to check the route logs for a database deadline or deployment configuration warning. Partner-facing errors carry the same generic 503 response.

Before enabling imports, verify the scheduled-pull monitor alerts the pilot operator on sustained 429 or 503 responses for this feed path. For 429s, check the `BrilStash feed rate limiter unavailable` warning by request ID. `trusted_client_ip_missing` calls for a check of the ingress's trusted client IP header. `distributed_limiter_unavailable` calls for a check of the deployment's Redis connectivity and health. A 429 without this warning means the caller has exhausted its bucket. Keep the limiter fail-closed during recovery and verify a complete pull after service returns.

Before recording handoff evidence, confirm the probe URL and the effective URL saved in BrilStash both use the approved deployment’s `BRILSTASH_FEED_HOST`. The operator verifies this deployment setting. The database checks the probe URL shape and requires the saved URL to match that recorded probe exactly.

Read the exact saved partner installation, configuration revision, and effective URL and query from BrilStash. With imports disabled, obtain evidence from its non-applying connection check or held auto-import that ties the request ID and `X-Baci-Catalogue-Correlation` to that exact saved configuration and, when held, to the immutable run, attempt, and result. The `X-Baci-Catalogue-Correlation` header is a public, unsigned correlation hash for log lookup only. Never use the header to authorize a request or verify payload integrity. Match the request ID against the independently trusted Baci server logs to confirm the non-secret key ID and generation. Those fields and the reviewed payload digest let you reproduce the correlation hash. The probe compares the full response digest with the reviewed snapshot to verify payload integrity. Store the approved evidence reference with `record-saved-connection`. This command records the operator’s attestation after independent partner readback. The local evidence format assumes BrilStash can return the request ID and correlation headers or provide equivalent verifiable evidence through an agreed protocol. Keep imports disabled until this capability is qualified.

- For a saved connection or immutable draft, use `check-handoff` with the probe and verification IDs immediately before any authorized conditional enablement. Ask BrilStash to enable exactly the verified configuration revision. Use `record-enablement-readback` to record the revision and both import controls observed at BrilStash, with an evidence reference and a stable observation UUID. Use `inspect-enablement` to compare the observed and verified revisions. Record the first catalogue import separately.
- For a held automatic import, record the exact attempt with `record-release-request` before sending any release. Use the verification ID returned by `record-saved-connection` and all corresponding generation and revision values. Then use `check-handoff` with the probe, verification, and release IDs. Release only the verified immutable result using BrilStash’s conditional operation. Keep future pulls and all other jobs held.
- If the generation, intended key, or relevant revisions changed, verify the current approved generation and saved connection again. If an action is indeterminate, check the exact partner revision or attempt before retrying.

Inspect `inspect-releases` for unresolved and overdue attempts. Record an acknowledged queue operation as `awaiting_application`. Use terminal dispositions only after the partner confirms exact application, cancellation or discard without application, or reconciled partial application. During suspension, cancel or contain potentially released attempts, verify withdrawal and reconcile before resuming.

Retire a wrong fresh binding with `retire-installation` and qualify a different fresh partner installation. For an activated installation, suspend it first and record verified partner disablement and final job disposition before retirement. Retirement revokes all keys and retains the installation and its history.

## Promote or suspend

Stage, inspect, and approve the exact candidate digest before closing reads. Calculate the latest closure as 23:30 Lagos minus 10 seconds for admitted responses, the confirmed partner drain and retry bound, and the promotion allowance. Start closure early enough for the commit and its observation to occur by that time. After the close command commits, run `observe-closure` with its closure revision. Use the returned time to start waiting for in-flight responses and, if relying on expiry, the additional partner retry and drain interval. The database enforces the dated window, closure revision, partner disposition, and candidate freshness. From 23:30 Lagos through the configured retry window the read gate requires enough freshness to cover the window. Reads always retain the 26-hour hard expiry from the source read. Keep a failed drain closed unless the recovery procedure proves the old generation can safely reopen.

For urgent withdrawal use `suspend` or `suspend-listings`. This closes reads and marks unresolved releases for withdrawal. Before `resume`, verify the partner-side off-sale result and disposition of all jobs that could restore the listing, then stage and approve a replacement. The normal scheduler cannot promote or restore serving.

When a previously published source becomes untracked but is still public with the same identity, use `approve-stock-withdrawal` with the listing’s existing external ID, the current catalogue revision, and the reviewed stock evidence. Stage a replacement, then review its unchanged ID and zero quantity. The prior generation stays unavailable until you promote the approved replacement through the relevant drain or recovery procedure. Use urgent withdrawal and retirement for an item that is private, repurposed, or recalled.

If a storefront migration changes an approved source ID, use `remap-listing` only after reviewing evidence that the replacement is the same sellable. It retains the external ID and previous source history. Review facts for the replacement source before building. The old generation becomes ineligible while it identifies the previous source.

## Qualification still required

Confirm category labels, NGN precision, bearer and request deadline behavior, saved-connection correlation and revision-bound enablement, selective release and terminal readback, importer treatment of failed pages, delayed retry or commit bounds, HTTPS reachability, and daytime stock exceptions with BrilStash. Qualify single-page imports before live rollout. Multipage paging in local fixtures does not qualify a partner crawl or late-commit protection.

## Database definitions after replay

- `20261119121900_brilstash_revalidate_storefront_and_ingress.sql` defines the effective page RPC. It returns `ingress_unavailable` when deployment proof fails. The earlier reader migration establishes the restricted owner and grants.
- `20261119121800_brilstash_bind_payload_display.sql` adds the generation insert guard. `20261119122000_brilstash_align_wire_shape.sql` independently excludes `model_number` in the SQL wire validator, matching the TypeScript schema.
- The paged SQL fixture stages, activates and reads a verified image URL with an uppercase host, trailing DNS dot and explicit HTTPS default port. Its output preserves the exact verified manifest spelling. Product URLs use the separate merchant-host and PDP checks.
- `20261119122100_brilstash_revalidate_served_product_paths.sql` shares the PDP path and exact variant or offer selection between staging and the serving eligibility check. A slug change after activation fails the pull until a replacement can be staged and promoted.
- `20261119122200_brilstash_guard_drain_abort_freshness.sql` keeps admission closed if the old generation cannot pass the read freshness check through the protected period and upcoming scheduled pull.
- `20261119122300_brilstash_pin_activation_prerequisites.sql` enforces the verified image sequence, qualified drain policy and five-minute first-activation evidence window. Restage and approve any candidate whose image sequence no longer passes the authoritative check.
- `20261119122400_brilstash_align_image_identity_and_activation_clock.sql` shares image deduplication rules with the builder and rechecks freshness and evidence after the last activation write.
- `20261119122500_brilstash_normalize_image_dns_root.sql` deduplicates verified image URLs whose host spelling differs only by a trailing DNS dot.
- `20261119122600_brilstash_require_selectable_offer_condition.sql` blocks the feed if an approved condition offer becomes hidden on the storefront because its normalized condition matches its parent.
- `20261119122700_brilstash_align_inventory_and_image_port.sql` limits verified HTTPS image ports to 1 through 65535.
- `20261119122800_brilstash_require_decremented_scalar_stock.sql` follows the order write for quantity-managed products and variants. Reconcile a null stock-management flag or missing `stock_quantity` before staging because either prevents checkout from decrementing a usable quantity. Include condition offers only for quantity-managed pools. Checkout rejects condition-selected offers on serialized pools even when their offer allocation is finite.

Full CI applies the registered migrations and runs the replay privilege and digest checks. The disposable PostgreSQL job also runs the BrilStash storage, assortment, and source fixtures in UTC and Africa/Lagos. Those fixtures exercise the effective late definitions for staging, activation, and reads.
