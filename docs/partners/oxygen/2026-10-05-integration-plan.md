## Proposed design — contingent on contract answers

### Configuration and identity

Use provider id `oxygen`. Resolve `(merchant_id, provider, environment)` to a protected connection record: partner identity, merchant reference, credential-secret reference, configuration version and readiness status. Store both reference and secret server-side, as the guide treats both as confidential. Public settings expose only availability and approved product/territory/amount constraints. A merchant toggle alone must not enable an unverified connection.

Support either individually onboarded merchants or a Baci partner with approved merchant mappings, but select the commercial account model with Oxygen before schema finalisation. Do not assume Ogabassey's production partner reference is reusable for other Baci tenants. Token caches, attempts, event identities and reconciliation lookups must all include connection and environment. Reject cross-environment evidence even if provider references collide.

Pin each attempt to an immutable connection version and provider account identity. Credential rotation, merchant reassignment or disconnect must not silently move existing loans to new credentials or beneficiaries. Separate disabling new applications from draining existing ones: retain authorised reconciliation access and old webhook verification material for the provider-defined overlap, then retire it. Shared-partner webhook registration belongs to the partner connection, not to each merchant toggle; a merchant settings update must not overwrite other merchants' callback configuration. Confirm endpoint lookup/registration idempotency and rotation procedure before automating provisioning.

Distinguish stable provider account identity from credential/configuration revision. A rotated key may authenticate access to the same existing account and loans; pinning an attempt must not force use of a revoked key. Resolve authorised current credentials for the pinned account. Deduplicate provider evidence by stable account identity, environment and provider-defined event identity; record the verification revision separately. Rotating credentials, reconnecting the same account or changing parser version must not reset replay protection. Confirm whether event IDs are globally unique or need additional resource/event-type scope before fixing the unique constraint.

Authenticated customer checkout is the proposed first release because it must resume a sensitive multi-step application. If guest support is required, use a short-lived, order-bound capability and prove it at every step; email plus order ID is insufficient. Do not use merchant owner/staff authentication for a customer loan. Resolve storefront merchant via trusted host/domain and check order ownership. Provider OTP establishes a provider step, not Baci order access.

For mobile requests to the shared API hostname, resolve merchant scope from the authorised persisted order/customer relationship; validate supplied merchant context against it. Do not require the shared API hostname to identify one merchant. Treat authenticated-only checkout, no split funding and a single-item pilot as proposed product restrictions requiring a decision in phase 1, not agreed business requirements.

User-facing requests use normal Supabase clients under RLS. Webhook/worker writes need a reviewed, least-privilege database boundary tied to verified provider evidence; define its caller role and grants explicitly. A publicly callable SECURITY DEFINER function accepting `verified: true` is not sufficient. No service-role exception is inherited. Any proposed privileged exception requires separate exact-scope owner approval; prefer a constrained worker role and atomic operations.

### Attempts and state

Persist an attempt before provider side effects: internal attempt ID, merchant/order/connection/environment, order version, expected invoice/payable amount and currency, references, local step, raw provider status code, idempotency/correlation identity, reconciliation timestamps and safe error code. Keep loan application progress, payment evidence, merchant settlement and fulfilment eligibility separate.

Proposed local progression: created → phone/customer validation and applicable selfie verification → eligibility pending/result → offer review/acceptance → booked → provider-required address verification and approval steps → equity/repayment requirements → activation. Model phone, selfie, address, eligibility, offer and financing statuses independently; the graph is not a single generic KYC boolean. The overview places address verification after booking, so do not require address completion before eligibility by assumption. Confirm ordering for new/existing customers and the prerequisites of approval/activation before coding. These are local orchestration concepts, not Oxygen's complete status enum. A local `indeterminate` result records uncertainty without inventing a provider status. Only provider evidence establishes decline, cancellation or provider expiry.

`BOOKED`, `APPROVED`, `ACTIVATED`, a browser return and completed repayment setup must not automatically produce `paid`, settlement ledger credit or dispatch. In particular, do not map Oxygen `APPROVED` directly to Baci `bnpl_approved`: existing database/consumer behaviour treats that status as consequential for inventory and order reuse. Keep order pending until the confirmed provider contract defines fulfilment evidence. Settlement requires separate authoritative evidence and reconciliation.

Enforce the Oxygen fulfilment decision at the shared mutation boundary, not only in checkout or the webhook. While a financing obligation is unresolved, manual ship-on-credit, confirm, payment-status edits, shipment booking and mobile-admin actions must not bypass it by changing ordinary order fields. Ordinary merchant permission to ship on credit is not evidence of Oxygen approval or settlement. Inventory/revenue side effects must also distinguish a manual payment label from verified provider evidence. If operations needs an exception, define a separate authorised resolution with evidence, actor, reason and liability treatment; never fabricate a provider status. This is a required Oxygen integration control, not a request to remove legitimate credit shipping for other payment methods.

Only one active financing attempt for an order version. Lock and validate amount, currency, inventory, cancellation, existing payment and eligibility before each irreversible action. A changed cart/address/price invalidates stale consent/quotes and requires controlled cancellation/re-application; never silently mutate a booked loan. Concurrent workers and duplicate webhooks use atomic unique constraints and an explicit transition graph. Preserve later authoritative reversals/refunds through compensating ledger events rather than treating all state changes as forward-only progress. Old attempts must not overwrite current ones.

The exclusion must cover other payment methods and order versions, not just Oxygen attempts. Order reuse, card/bank initiation, wallet/savings finalisation, staff record-payment and other BNPL entry points must respect the same unresolved financing obligation. A new order version does not extinguish a previously booked loan. Changing methods requires authoritative cancellation/no-liability evidence or an operations resolution. Already-issued bank references can still receive late funds: route duplicate funding to reconciliation rather than silently paying twice or activating another loan. Use an atomic intent/lease around provider actions, without holding a database transaction open during network calls; revalidate the version when committing the result.

Inventory needs an explicit bounded lifecycle before the first provider request. Define KYC/application deadlines, reservation extension rules, quote validity and a maximum hold; inspect both ordinary stock decrement/restoration and serialized-unit reservations. A local deadline must not imply provider cancellation. On expiry with an unresolved loan action, freeze further activation and request reconciliation; release/reallocate stock only under the agreed cancellation or liability policy. Before activation, recheck availability and the agreed fulfilment conditions. If provider success arrives after stock release, hold dispatch and open remediation rather than substituting a device silently. Include Oxygen deliberately in cleanup/monitoring logic; periodic status polling must not extend a hold indefinitely through `updated_at` writes.

Timeout after create/book/approve/activate/cancel is indeterminate. Persist the action intent and reconcile by a provider-supported correlation/status lookup; never blindly retry it. Local idempotency prevents duplicate Baci submissions but cannot guarantee exactly-once creation at Oxygen. If Oxygen cannot resolve ambiguous actions, stop that attempt for operations review.

A worker lease expiring also does not prove that its provider call failed. A replacement worker must reconcile the existing action intent before sending another mutation; lease/version fencing prevents stale local writes but cannot undo an already accepted external loan action. Reuse provider idempotency keys only according to the confirmed provider contract. Financial evidence for a superseded attempt is still recorded against that attempt and raised for remediation: suppress its effect on current checkout/dispatch, not its existence as a financial obligation.

### Eligibility and bank-statement boundary

Oxygen owns the credit decision. The documented application carries personal identity, bank-account and declared employment/salary fields; the overview places phone/selfie validation before the eligibility lookup. `POST /v1/loan-request/get` returns an example with `successful`, `eligible` and `eligible_amount`, or a 400 example reporting credit-score retrieval in progress. The docs do not identify its underwriting data sources, whether statements are fetched internally, or whether a customer must link/upload a statement. Do not infer transaction access from BVN/account details and do not implement Baci credit scoring as a substitute.

Before phase 3 is considered complete, Oxygen must confirm one of: statements are not required for this product; Oxygen collects them through a documented internal/hosted consent flow; or Baci must support a documented secure upload/link and processing-status flow. If required, integrate that prerequisite at Oxygen's specified stage and keep statements outside model context and transcripts. A missing statement contract is an unresolved scope dependency, not permission to repurpose `residency_document`. Receipt of address evidence is not proof of completed underwriting.

| Observed result / condition | Proposed Baci behaviour | Required contract |
| --- | --- | --- |
| Valid affirmative decision and finite positive eligible amount | Show the authorised customer Oxygen's reported limit; continue only if the chosen principal is within it and an offer is available. | Units/currency, limit scope, expiry and allowed reuse across applications. |
| Explicit negative decision | Show a provider-approved neutral decline message; do not invent a reason or immediately resubmit. | Negative schema/codes and reapplication policy. |
| Credit-score processing example (`400`, code `99`) | Treat the documented shape as a pending candidate, never all HTTP 400s; keep the existing request reference. | Stable pending code semantics, polling interval, maximum wait and escalation. |
| Network error, auth expiry, 429 or 5xx | Keep decision unknown; refresh authentication if needed and retry only the status lookup within confirmed limits. | Confirmation that repeated POST lookup is read-only, rate limits and retry guidance. |
| Missing/contradictory fields, unknown code or stale decision | Stop automatic progression and reconcile; neither approve nor declare a decline. | Complete response schema and freshness/version semantics. |
| Limit below desired financed principal | Explain insufficient limit for this selection; offer a smaller eligible basket only under confirmed rules. | Equity/top-up or amended-application contract; no automatic extra loan or split funding. |

Persist when a decision was observed and any provider-issued validity/version metadata. Recheck expired decisions at the documented stage. Do not assume that an example eligible amount is a guaranteed offer, a reserved credit balance or funds available to the merchant. Concurrent orders cannot rely on a cached limit as though it were independently spendable for each. Avoid inventing a local credit reservation ledger; Oxygen must confirm how booking enforces customer-wide exposure.

### Invoice and settlement

Use integer minor units inside the Oxygen orchestration/money contract; implement provider conversion only after Oxygen confirms its units and NGN support. Existing Baci order/transaction/settlement amounts use their established units: for example, the paid-order settlement executor converts gross major units to kobo for calculation and back for its RPC. Define and test conversions at each existing database/API boundary, including exact decimal handling and safe integer bounds. Do not change shared column units or send kobo to a naira field. Freeze an invoice breakdown: devices, tax, delivery, discount, approved financed amount and any customer equity. Confirm whether `loan_amount` means gross invoice or financed principal. Do not reuse existing provider BNPL min/max thresholds, platform fees or underpayment tolerance.

Eligibility amount is not a customer-approved loan offer. Obtain the authoritative offer/repayment schedule contract or provider-hosted disclosure: principal, equity, interest/fees, instalment amounts/dates, total repayable, expiry and terms version. Present these before approval and bind customer acceptance to that exact offer and invoice version. Requote/reconsent when either changes. The reviewed API pages do not show how to retrieve a complete offer; do not calculate or invent Oxygen's terms or treat a generic `accept_terms_and_condition: yes` as consent to a later unknown offer.

For the initial release, propose disabling wallet, device-savings, store-credit split funding and mixed unsupported product baskets with Oxygen until its equity contract explains their interaction. Do not treat customer equity paid to Oxygen as money received directly by Ogabassey. Booking currently shows one product object; multiple-item invoices need an explicit provider contract or a clearly communicated single-item pilot restriction.

Maintain the supplied no-merchant-deduction requirement; do not silently apply Credit Direct/Klump/Paystack fee calculations or record a platform payout liability for funds Oxygen settles directly to the merchant. Agree ledger treatment, payout evidence, timing, reversals, partial refunds, delivery failure and warranty returns with Oxygen and finance. Reuse inventory confirmation/cancelled-order recovery concepts only after access-boundary review. Late financial success on a cancelled order opens reconciliation without reopening fulfilment.

### API and client boundaries

Candidate Baci API namespace: `/api/payments/oxygen/attempts` for initiation, order-scoped step actions/status/cancel, and `/api/payments/oxygen/webhook` for inbound evidence. Names are design proposals, not existing routes. Zod schemas live in `apps/web/src/schemas/`; provider transport and orchestration live in focused `apps/web/src/lib/payments/oxygen/` modules; cross-app safe contracts belong in `packages/shared`.

Keep provider login, reference mapping, validation and financial transitions server-side. Do not expose a generic provider API proxy. Apply rate limits to initiation and OTP actions, validate malformed JSON, return safe errors and avoid logging bank/BVN/NIN, selfies, OTPs, signatures or signed URLs. Prefer provider-hosted KYC and repayment pages when supported. Confirm consent text, retention/deletion policy and data responsibilities before collecting extra identity information; Baci checkout currently lacks this complete loan application UX.

Validate exact redirect origins per environment, bind return state to attempt/customer, and resume by reading server state. A closed window, denied camera permission or network loss is resumable rather than paid/declined. WebView messages remain navigation hints. Use an external browser fallback only after confirming provider support and secure return handling. No broad wildcard host allowances.

The event inbox must also cover deliveries that arrive before the provider reference is committed locally or while the originating request outcome is unknown. Persist authenticated unmatched evidence safely for later correlation, with bounded retries and an operations queue; never create merchant/order mappings from untrusted event fields. Correlate through the registered connection and stored references. Persist only necessary normalised financial/status fields and a payload hash; any retained raw evidence needs restricted encrypted storage and a retention policy. Provider verification and local mutation failures remain separately observable. Exactly-once local ledger/stock effects require database constraints and transactions; delivery to external email/push systems is retryable and may duplicate unless that destination supports idempotency.

Define webhook acknowledgement separately from completion: only acknowledge valid evidence after durable inbox storage, subject to Oxygen's required acknowledgement contract. Database unavailability must not return a misleading success. A duplicate durably stored event can be acknowledged while an incomplete worker job resumes. Quarantine conflicting contents under the same event identity, and resolve webhook-versus-status-lookup disagreement through authoritative provider reconciliation rather than arrival order. Alert on inbox backlog, unmatched references, unresolved mutations and settlement overdue against agreed deadlines, with an assigned operations owner. Do not promise eventual recovery without a provider lookup contract and an implemented worker schedule.

### Chat-led integration option

The separate provider endpoints support a proposed chat-led orchestrator: gather checkout intent → open a secure application form → validate customer/phone and applicable selfie → check eligibility → display the exact offer → book → complete address verification and OTP/signature approval in the provider-confirmed order → confirm equity/repayment requirements → activate under the agreed conditions → show verified application/payment progress. Insert bank-link/statement consent only if Oxygen confirms it is required and provides the contract. This is an architectural inference from the modular API, not a documented Oxygen chatbot product or permission to skip stages.

Keep conversational state separate from durable attempt state. Bind every chat session/action to the authenticated customer, tenant and order; recheck access on resume and after account changes. The assistant may explain and offer the next allowed action, but server code enforces prerequisites, amounts, transitions and idempotency. Explicit customer acceptance must precede any step that creates an obligation; ask Oxygen whether booking itself creates one. A model-generated statement or tool selection cannot substitute for consent, OTP approval, signature or payment evidence.

Do not put BVN/NIN, bank details, OTPs, signatures, residency documents or token-bearing KYC URLs into model context, chat transcripts, analytics or tool logs. Use protected form/action components and return only safe progress codes to the chat orchestrator. Hosted KYC/camera and signing remain secure interactions outside ordinary text chat. Chat disconnect, repeated messages and tool timeouts must resume the same attempt rather than create another loan. Add tests for repeated approve messages, stale buttons, session/account changes and interrupted hosted steps. No chat implementation is part of the present review.

The proposed initial chat path is tied to a selected device and order. A general “what can I borrow?” flow before order creation is a separate product choice: establish whether Oxygen permits reusable prequalification, its consent/cost implications, validity and later order binding before adding it. Modular endpoints do not establish that permission. If chat is selected, use the same backend orchestrator as checkout with structured allowed actions, safe statuses and authenticated secure-form handoff. Bind each actionable card to the current attempt/offer version. Model fallback or chat timeout must leave that durable state intact and direct the customer to a deterministic status page.
