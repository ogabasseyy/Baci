# S10: Legacy wallet migration scripts

## What changes
The owner moves the few customers who still hold money in the old in-app wallet by hand. This change supplies a read-only balance list, a single reviewed zero-out update, and a step-by-step runbook. Nothing runs automatically and no agent runs these files.

## Why
PiggyVest holds the money. The old wallet must be emptied exactly once for each customer, only after the owner has credited that customer in PiggyVest by hand.

## What could go wrong and how it is prevented
- Money zeroed without a matching credit: the update only takes rows the owner lists, one PiggyVest reference each. A reference cannot be used twice in one run or reused later.
- Balance changed between the list and the update: wallets are locked first, then the exact balance is checked again. Any difference stops everything.
- Stored balance and ledger disagree: the list marks such wallets ineligible, and the update re-adds the ledger and refuses a wallet that does not agree, so a later rebuild cannot bring the money back.
- Unsettled activity: wallets with pending ledger rows are refused, and the runbook says to let in-flight airtime purchases and refunds settle first.
- Balances too large for the update are marked ineligible in the list, before anyone is credited.
- Wrong row counts: exactly one declared count is required and it must equal the rows loaded.
- Second run for the same wallet is refused. The wallet's last-changed time is updated.
- Everything is one transaction and ends in a rollback until the owner swaps in the commit.

A credit that was already waiting on a wallet when the update ran could land just after it. The runbook keeps the pause in place after the commit, asks for a final list check at least an hour later, and says never to credit PiggyVest a second time if a migrated wallet shows money again.

## How it is tested
The real scripts run against a scratch PostgreSQL database in two test files: one for the list and one for the update. They cover the happy path, the dry run, each refusal above, and expired expiry rows. CI now installs PostgreSQL and requires these tests to run, so they cannot be skipped silently.

## How it stays switched off
These are documents and scripts only. No application code calls them, and nothing is applied to production by this change. The owner must run them by hand.
