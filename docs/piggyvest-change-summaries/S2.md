# S2: master kill switch for new-money paths

## What changes
One environment setting, the master kill switch, now stops every way new money can enter the PiggyVest wallet. This includes the three webhook intake points that queue provider deposits, signed card events and paid interest. It also covers the existing per-feature gates and the two prefunded first-card rails (checkout and contributions), which start new card payments into a savings goal. The read-only wallet view keeps working while the switch is on.

## Why
During an incident the owner needs one switch that stops new deposits at once.

## What could go wrong and how it is prevented
- A module reads its own enable flag and skips the switch. A sweep test now scans the TypeScript and JavaScript files in the web source, the web and repository tools and the repository scripts (not other apps, packages, the web package root, or non-JavaScript tooling such as Python activation bundles), and fails if any scanned file reads an enable flag directly (including aliased, renamed, destructured, reflective or computed-name reads, the card rails and reads through the flag registry) or builds a flag name at run time. It also fails if a scanned folder goes missing or shrinks. The staging launcher copies a killed switch into the worker it starts, so that worker refuses new checkouts.
- The sweep is an early warning, not the guarantee. The runtime gate and the behaviour tests run with the switch on are the real protection. Further regex-shape evasions, such as aliases or environment objects held under other names, are an accepted limitation.
- Inbound deposits are deferred, not dropped, while killed. A bank inflow, custody-signed card outflow or interest payout delivery answers a retryable 503 (PIGGYVEST_KILL_SWITCH_ACTIVE) before any intake or legacy credit runs, PiggyVest redelivers, and the deposit is recorded exactly once after the switch is lifted. The money already sits at PiggyVest.
- Money already accepted by the provider could be stranded. The workers and drain readers never consult the switch, so accepted deposits still settle.
- Customers could be locked out. The wallet view falls back to the read-only reader under the switch, but only when the wallet feature itself is still switched on, and wallet setup recovery, which can promote a wallet, is skipped. Review holds still show to the customer while the switch is on.
- A customer who already paid a first-card checkout could not finish it while the switch was on. Refreshing an existing checkout now stays available; only starting a new one is refused.
- Plan funding keeps accepting a flag value padded with spaces, as before. No other flag accepts padding.
- Cancel to main and reconcile are untouched and stay available. A test follows everything they use, not just their own files, and fails if any of it consults the switch.
- A typo in the switch value fails closed, since only unset or exactly false means off.

## How it is tested
New tests cover each intake gate, both prefunded card rails, with the switch on and off, the worker and drain readers under the switch, the wallet view under the switch, and the sweep for direct flag reads.

## How it stays switched off
No new setting is turned on by this change. Every feature flag keeps its current default, so nothing new is active in production. The switch only ever restricts.
