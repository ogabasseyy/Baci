# S3: PiggyVest deposits go to the PiggyVest ledger only

## What changes
When money arrives in a customer's PiggyVest wallet, by bank transfer or by card funding, we now write one receipt in the PiggyVest receipt ledger and nothing else. We no longer add that amount to the customer's old wallet balance, and we no longer write an old wallet history line for it. A new guard also refuses any attempt to write a deposit line into the old wallet history, so a later edit cannot quietly bring the old behaviour back.

## Why
PiggyVest holds the money and is the record. If we also added each deposit to the old balance, the same naira would be counted twice, and the manual move of legacy balances would be thrown off. Old balances stay exactly as they are until the owner credits them by hand and zeroes them in one reviewed update.

## What could go wrong and how it is prevented
- A deposit counted twice: the receipt is still keyed by the provider's transaction, so replays are ignored, and a replay with different details is held as a conflict.
- A reused event number for a new transaction: still refused as a conflict, as before.
- A deposit for an unknown or unverified wallet: still not recorded, as before.
- Someone re-adds the old credit later: the guard rejects the write, and a catalog test fails if either function names the old wallet tables again.
- Money seems missing from the old balance: that is intended. Balances now come from PiggyVest. The old transfer-from-main-wallet-to-goal path checks the old balance, so it now answers "insufficient" and cannot move money. Goal funding uses each goal's own PiggyVest wallet.
- Refunds, savings holds and releases are separate paths and are untouched.

## How it is tested
Two isolated database checks run real migrations. One sends a bank deposit through, including a replay, a changed amount, a reused event and an unknown wallet. The other settles a card funding. Both prove the old balance and old history are unchanged and exactly one receipt exists. Both were run first against the old behaviour and failed. A contract test for the full database replay checks the guard exists and that the two functions no longer touch the old tables.

## How it stays switched off
Deposits are only applied once the engine readiness check says yes, and today that check always says no. The inflow and bank-inbox switches are off in production. This change adds no switch and turns nothing on.
