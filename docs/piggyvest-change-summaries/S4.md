# S4: hide goal account numbers and alert on unmapped deposits

## What changes
Savings goals no longer show a bank account number anywhere in the app, for any customer. The wallet screen no longer looks up or displays a goal account, the plan funding screens no longer keep the number in memory, and the customer is told to fund a plan from their wallet. The app names PiggyVest in that note only when the merchant has an explicit primary verdict.

When a bank deposit arrives for a PiggyVest wallet that matches none of our goals or wallets, an operator alert is raised once per deposit. The deposit is not credited and stays retryable.

This PR also changes the primary contribution path, all behind the dark primary flags:
- A stored contribution id is bound to the rail (PiggyVest or legacy) of the attempt that created it, written before the request is sent. A retry stays on that rail. An id with no recorded rail is checked against PiggyVest first and goes to legacy only if PiggyVest has no record of it.
- The status route answers a merchant that is not the primary-savings merchant with a distinct 409 SAVINGS_MERCHANT_NOT_PRIMARY, so a stored id there goes to legacy instead of blocking.
- The goal reminder is cancelled by the rail that handled the contribution.
- The top-up minimum is applied when funding the first contribution.
- If the server asks for a wallet PIN, the app refuses cleanly with a "coming soon" message, keeps the stored id and rail, and does not retry.

## Why
Money sent by bank transfer straight to a goal account does not reach the goal. Hiding the number removes that risk.

## What could go wrong and how it is prevented
- A goal account number could still show on an old screen. The wallet hero screen that did this is removed, and tests assert no goal account number is fetched or shown.
- A retry could debit twice through the other rail. Rail binding prevents it, and an unknown status keeps the id and waits.
- An alert could be repeated or missed. It is raised once per deposit per server instance, and a failed alert is retried on the next delivery. It never changes whether the deposit is credited.

## How it is tested
Tests cover the wallet screens (no account number requested or shown), the rail rules, the PIN refusal, and the neutral wording with PiggyVest off. Webhook tests cover the alert being raised once and the retry outcome when the alert fails.

## How it stays switched off
The primary path runs only when the primary flags are on, and they stay off in production. No production setting changes.
