# Ask for the PIN before money moves into a savings goal

Task: S5
Owner sign-off: not required (ships switched off; no live payments)

## What changes

Moving money from the wallet into a savings goal now needs a PIN check.
The customer enters their transaction PIN, the server checks it and hands
back a short-lived proof, and the goal funding step spends that proof in
the same database step that sets the money aside. The proof is for one
goal, one transfer and one amount. A new route performs the PIN check.

Proof types for cancelling and completing a goal are also added, with the
database helper that will spend them. Those two flows are not connected
yet. That is a planned follow-up, because the database has no goal cancel
or complete step to attach them to today.

The database login that runs savings transfers can no longer call the old
funding step directly. It can only use the new one that demands the proof.

## Why

A stolen session should not be enough to move money into a goal. The PIN
is a second factor the thief does not have.

## What could go wrong and how it is prevented

- A transfer set aside without a proof: the proof is spent in the same
  step, and a refused proof undoes the transfer completely.
- A proof reused or used for a different amount or goal: each proof is
  single use and tied to the exact goal, transfer and amount.
- An old proof used late: proofs last two minutes, and the clock is read
  after the proof is locked.
- Retrying a transfer already set aside: it needs no second proof and
  spends none.
- Guessing the PIN: the existing lockout applies after five wrong tries.

## How it is tested

Database tests check refusal when the proof is missing, unknown, expired,
for another amount, purpose, goal or transfer, or when the merchant is
switched off. In each case nothing is set aside and the proof stays
unspent. They also check that the exact proof reserves the transfer and is
spent, that a replay needs no proof, that a spent proof cannot fund another
transfer, and that the login cannot call the old step. Unit tests cover the
route and the proof binding.

## How it stays switched off

The PIN secret is not set and no merchant has PIN checking enabled, so no
proof can be issued and funding through this path is refused. Nothing is
enabled in production by this change.
