# Ask for the PIN before money moves into a savings goal

## What changes

Moving money from the wallet into a savings goal now needs a PIN check. The
customer enters their transaction PIN, the server checks it and hands back a
short-lived proof, and the funding step spends that proof in the same database
step that sets the money aside. The proof is for one goal, one transfer and one
amount. A new route performs the PIN check, and for funding it first confirms
the customer has savings on and the goal is theirs and active.

Proof types for cancelling and completing a goal are added too, with a
database helper. Those flows are not connected yet.

The savings login can no longer call the old funding step directly. A
merchant with PIN checking off keeps funding with no proof, as before.

## Why

A stolen session should not be enough to move money into a goal.

## What could go wrong and how it is prevented

- A transfer set aside without a proof: the proof is spent in the same step,
  and a refused proof undoes the transfer completely.
- A proof reused, or used for another amount or goal: each proof is single use
  and tied to the exact goal, transfer and amount.
- An old proof used late: proofs last two minutes.
- Retrying a transfer already set aside: no new proof is needed if one was
  already spent for it. If it was set aside while checking was off and is still
  waiting to be sent after checking is switched on, a proof is required first.
- A cancel or complete proof spent with nothing else happening: the helper
  refuses loudly on anything but a spent proof, so a caller cannot carry on.
- Proofs piled up for goals that are not the customer's: refused up front.

## How it is tested

Database tests check refusal for a missing, unknown, expired or mismatched
proof, or a merchant switched off, leaving nothing set aside. They check that
the exact proof works, that a replay needs no second proof, that a waiting
transfer is held back until a proof is spent once checking is on, and that
cancel and complete proofs are spent only for the customer's own goal. Unit
tests cover the route, the goal check and the proof binding.

## How it stays switched off

PIN checking is off for every merchant and the PIN secret is not set, so
funding behaves as it does today. Nothing is enabled in production by this
change. Turning PIN checking on for a merchant must wait for the phone PIN
screen.
