# S6: cancel a savings goal and refund the whole balance to the main wallet

## What changes
A customer can cancel a savings goal and get everything in it, interest included, back in their PiggyVest main wallet. First the server hands out a one-off attempt number. Then the customer types their PIN, and that proof is tied to that goal and attempt. The server asks PiggyVest what the goal wallet holds at that moment and moves exactly that amount. We never work out interest ourselves. Once PiggyVest confirms, the goal is marked cancelled in the same database step. Nothing can be added to a goal while its cancel is under way or done.

## Why
PiggyVest holds the money, so cancelling must be one checkable transfer that cannot happen twice or start from an old or borrowed PIN proof.

## What could go wrong and how it is prevented
- Double tap or retry: the transfer reference is built from the goal, so PiggyVest cannot move the money twice. Only one cancel per goal can be live.
- Timeout: we never send again. A retry only asks PiggyVest about that reference. A "not found" straight after sending is treated as uncertain.
- Failed transfer, then retry: once a sent attempt is released as failed, the next try gets a numbered reference, so an old failed record cannot block it. Attempts never sent keep the plain reference.
- Late success: if PiggyVest shows the transfer as done only after we released it, the verified record still settles that attempt and cancels the goal. If a newer try is already live, it is flagged as a conflict for a person to review.
- Stale or borrowed PIN proof: it only works for an attempt number this database issued for that goal and customer, and is spent in the same step that reserves the attempt.
- Wrong wallets: both wallets are re-read and must belong to the same customer and business before money moves.
- Cancel stays available: it ignores the kill switch and flags, but needs the PIN.
- Open point: confirm with PiggyVest in sandbox that numbered references work.

## How it is tested
Database tests cover the attempt number, numbered retries, late success, every wrong PIN binding, expiry, replays, settlement mismatches and failed transfers, and check permissions in the catalog. Unit tests cover one-shot sending, timeouts and ambiguous failures. All mocked; no live call was made.

## How it stays switched off
Nothing turns anything on. The mobile app does not call the new route yet, and the complete action is still refused until S7. The route needs PiggyVest runtime settings that are not set in production.
