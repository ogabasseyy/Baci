# S6: cancel a savings goal and refund the whole balance to the main wallet

## What changes
A customer can now cancel a savings goal and get everything in it, interest included, back in their PiggyVest main wallet. Cancelling takes two steps. First the server hands out a one-off attempt number. Then the customer types their PIN, and that PIN proof is tied to that goal and that attempt number. The server asks PiggyVest what the goal wallet holds at that moment and moves exactly that amount. We never work out interest ourselves. Once PiggyVest confirms, the goal is marked cancelled in the same database step. Nothing can be added to a goal while its cancel is under way or done.

## Why
PiggyVest holds the money, so cancelling must be one checkable transfer that cannot happen twice or start from an old or borrowed PIN proof.

## What could go wrong and how it is prevented
- Double tap or retry: the transfer uses a reference built from the goal and the word cancel, so PiggyVest cannot move the money twice. Only one cancel per goal can be live at once.
- Timeout: we never send again. A retry only asks PiggyVest for the status of that reference. A "not found" answer straight after sending is treated as uncertain, not as proof that nothing was sent.
- Stale or borrowed PIN proof: the proof only works for an attempt number this database issued, for that goal and customer, and is spent in the same step that reserves the attempt. A made-up attempt number spends nothing.
- Wrong wallets: both wallets are re-read from PiggyVest and must belong to the same customer and business before any money moves.
- Cancel must not trap people: it ignores the master kill switch, the feature flags and the customer savings setting. It still needs the customer's PIN.
- Open point for the sandbox run: if PiggyVest reports a cancel transfer as failed, a retry reuses the same reference. We have not yet seen how PiggyVest treats a reused reference.

## How it is tested
Database tests cover the attempt number, every wrong PIN binding, expiry, replays, settlement mismatches and failed transfers, and check permissions in the catalog. Unit tests cover one-shot sending, timeouts, ambiguous failures and both routes. Everything uses mocks; no sandbox or live call was made.

## How it stays switched off
Nothing turns anything on. The mobile app does not call the new route yet, and the complete action is still refused until S7. The route needs the PiggyVest runtime settings, which are not set in production.
