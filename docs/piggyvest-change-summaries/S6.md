# S6: cancel a savings goal and refund the whole balance to the main wallet

## What changes
A customer can cancel a savings goal and get everything in it, interest included, back in their PiggyVest main wallet. The server hands out a one-off attempt number, the customer types their PIN, and that proof is tied to the goal and attempt. The server asks PiggyVest what the goal holds and moves exactly that. We never work out interest ourselves. Once PiggyVest confirms, one database step cancels the goal and credits our wallet records. A goal under cancel cannot be added to or spent.

## Why
PiggyVest holds the money, so cancelling must be one checkable transfer that cannot happen twice or start from a borrowed PIN proof, and our records must agree with PiggyVest's.

## What could go wrong and how it is prevented
- Double tap or retry: the transfer reference is built from the goal, so the money cannot move twice. Only one cancel per goal can be live.
- Timeout or closed app: we never send again; a status check or PiggyVest's notification finishes the cancel.
- Failed transfer, then retry: the next try gets a numbered reference. A reference is never reused: the next number is one more than the highest ever issued for the goal, and the database enforces that references are unique.
- Late success: if PiggyVest shows a transfer as done only after we released it, a status check settles only that refund's own amount. If the goal was funded again meanwhile, or money still sits at PiggyVest after any refund, the attempt is marked "under review" (not confirmed): only that refund's own amount is credited, the goal stays open, a person is alerted and every status check keeps saying "under review". A new cancel waits until an operator clears the review, and then the customer can cancel again.
- Money counted twice: an order cannot spend a goal under cancel, and the refund reaches our records exactly once.
- Mixed goals: a goal tied to a PiggyVest wallet no longer accepts old-style contributions or order spending, because those change only our records. A goal that already holds either is never refunded; the customer is told it needs review and a person is alerted.
- Invented attempt number: refused.
- Balance above the automatic limit: nothing is sent and the customer is told to contact support.

## How it is tested
Database tests cover refusals, numbered retries, late success, PIN bindings, replays, wallet credit, reconciliation and permissions. Unit tests cover one-shot sending, timeouts, alerts, settlement failures, notifications and schemas. All mocked; no live call was made.

## How it stays switched off
Nothing turns anything on. Cancel returns the customer's own money, so the master kill switch and the new-money switches never block it. One narrow emergency exception: PIGGYVEST_GOAL_CANCEL_DISABLED (off by default) refuses new cancels, including the PIN step that starts one, with 503 while status checks and settlement keep running. The goal-wallet triggers only affect goals already tied to a PiggyVest wallet. Daily reconciliation expects funding minus settled refunds, never below zero, so a refund that includes interest cannot invalidate the whole check. Scheduled card debits skip goals tied to a PiggyVest wallet, and one goal failing no longer stops the others.
