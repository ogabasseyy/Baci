# S7: complete a savings goal, then save the purchase request before alerting the owner

## What changes
A customer whose goal has reached its target or end date can complete it. The server hands out a one-off attempt number, the customer types their PIN, and that proof is tied to the goal and attempt. The server asks PiggyVest what the goal holds, interest included, and moves exactly that to the customer's main wallet. Once PiggyVest confirms, one database step marks the goal completed, credits our wallet records and saves a purchase request: the goal, its target and the customer. Only after that is saved is the owner alerted. The goal stays completed. The owner finishes the order by hand. There is no checkout, wallet spend or bank payout.

## Why
PiggyVest holds the money, so completing must be one checkable transfer that cannot happen twice, and a failed alert must never lose the customer's request.

## What could go wrong and how it is prevented
- Double tap or retry: the transfer reference is built from the goal, so money cannot move twice.
- Timeout: we never send again; a status check finishes it.
- Failed transfer, then retry: the next try gets a new numbered reference, never reused.
- Too early: the goal must have reached its target or end date. This is checked when the attempt starts, before the PIN is used, and before sending.
- Money left over or late success: the attempt is marked "under review", only that transfer's own amount is credited, the goal stays open, no purchase request is made and a person is alerted. A person clears it before the customer can retry.
- Alert fails: the request is already saved, so nothing is lost. The alert repeats on the next status check.
- Clashes: while a complete runs, the goal cannot be added to, spent or deleted, and a cancel cannot start. A goal that also holds old-style money is never completed.

## How it is tested
Database tests cover eligibility, PIN binding, numbered retries, late success, review, the saved request, alert state, wallet credit, reconciliation, fences and permissions. Unit tests cover one-shot sending, status checks, failing alerts, routes and schemas. All mocked; no live call was made.

## How it stays switched off
Nothing turns anything on. Complete returns the customer's own money to their own main wallet, so the master kill switch and the new-money switches never block it, as with cancel. One narrow exception: PIGGYVEST_GOAL_COMPLETE_DISABLED (off by default) refuses new completes, including the PIN step, while status checks and settlement keep running. Daily reconciliation expects funding minus settled refunds and completions, never below zero.
