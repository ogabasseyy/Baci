## Notes for the owner (written by hand after the run)

Everything above this section was written by the harness and checked by its leak scan. This section was added afterwards. No ids, account numbers, keys or balances appear in it.

### How these runs were made

- Where: the PiggyVest sandbox only, with a sandbox test key. The harness refuses any other host and any key that is not a test key. Nothing touched production, Vercel, the VPS or real PiggyVest accounts.
- Who: a new synthetic QA customer made for this task (synthetic BVN, `example.test` email, `+234000` phone). Money calls were allowed only for the length of the run, and each one was journaled first and sent once.
- Which proofs: P1 to P6, P8 and P9. P7 (interest routing at creation) was left out on purpose because it has its own follow-up run.
- Two passes on the same QA customer. This file is the first. `2026-11-02-2.md` is the second (`--new-attempt`), made after the bank-destination check and the bank refusal message were added to P4.
- An earlier pass the same day, on a different new QA customer, could not run any of the transfer proofs. The sandbox accepted the goal sub-wallet (HTTP 202), but the wallet never showed in the customer's wallet list, even 25 minutes later. That pass is not committed. It shows that sub-wallet creation in the sandbox can stall without any error.

### What these runs settle

- P1: a repeat create with `returnIfExist=true` returns the same customer and the same default wallet. This is checked against this run's own create. We also tried a create that reuses an existing BVN with a different `third_party_identifier`, email and phone. It returned the existing customer and its default wallet with `new_customer:false`. The new identifier was not saved anywhere (a lookup by it finds nothing), and the original customer kept its own identifier. So `returnIfExist` matches on the BVN. Onboarding must treat an unexpected `customer_id` with `new_customer:false` as a customer it does not own, and never adopt it.
- P2: we re-sent the same reference straight after it settled. The sandbox refused it with HTTP 400 ("Reference already passed, Please try again in a few minutes"). Nothing was debited a second time and no second record appeared. Both passes agree. The wording suggests the check may only last for a limited time, so a reference must still be used only once.
- P3: the goal deposit landed in the goal wallet, gross, with a fee of 0 (the same as on 31 Oct). The business sandbox wallet passed the harness's unbound check, which at the time accepted either `api_customer_id: null` or a readback without that key (this run did not record which). The harness now admits only an explicit `null`, so the next run confirms it. A test deposit into it shows as a `bank-inflow` credit row, gross, fee 0. That deposit's own record (GET /transaction/:id) carries a `customer_id`; it was not compared with the QA customer in this run.
- P4: a wallet-to-wallet transfer leaves `withdrawal_count` unchanged. The bank outflow was refused in both passes. The second pass shows why. The bank code is in the sandbox bank list and the account resolves, but the sandbox says the business's transfer-fees wallet ("Expense Profile (Main)") has no funds. So, in the sandbox at least, the bank-transfer fee is charged to a business fee wallet rather than the customer's wallet.
- P5: no interest accrues at the sandbox's 0% rate, so this is still unobservable. The first real monthly payout (1 December at the earliest) remains the release check.
- P6: the sandbox charges 0 on deposits and on wallet transfers. The wallet readback has `is_frozen` and `has_an_active_lien` flags.
- P8: we checked Collection to main, main to goal and goal to main. Each time, the receiving wallet gets its own `credit` row (category `p2p`) that carries our reference and names the sending wallet. That row has its own id, not the id the sender's status check shows. It does share `reference` and `third_party_reference` with that record, and looking up the sender's transaction id from the receiving side also works. Both passes agree.
- P9: for both the main and the goal deposit, the record shows `amount` and `fee`, the amount is the gross, and the balance rose by the gross. Because the sandbox fee is 0, we still cannot prove whether a real fee would be taken out of the deposit.

### Until proven, the safe behaviour stays in place

- A reference is never sent twice. A failed or uncertain transfer is released, and any retry uses a new reference.
- If the receiving wallet of a wallet-to-wallet transfer ever gets an inflow event, it is never counted as a new deposit. Unknown inflows go to review.
- Any deposit whose fee is not zero, or whose fee and balance change do not match, goes to review. Nothing is settled automatically.
- A `customer_id` that comes back with `new_customer:false` and does not belong to the person signing up is never adopted.
