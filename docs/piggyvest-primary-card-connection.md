# PiggyVest primary wallet: Paystack card connection

## Current gap and implemented boundary

`apps/mobile-storefront/components/wallet/WalletFundPanel.tsx` retains the card toggle and prefilled card amount. Its `onFund` path reaches `fundWallet` in `wallet-screen.handlers.ts`, which calls `initializeWalletTopUp` in `lib/wallet-top-up.ts`. The funding-account controller changes bank-account presentation; it does not change card custody.

`apps/web/src/app/api/storefront/customer/wallet/top-up/initialize/route.ts` still creates a `WAL-` reference with `transaction_type: wallet_topup`. Its confirm/webhook flow belongs to the existing customer-wallet ledger. Displaying a PiggyVest bank account does not make these card credits PiggyVest-backed. This route also constructs an admin client; do not copy that user-operation pattern into the new connection.

New scoped files implement a staging-only verification and ledger adapter:

- `apps/web/src/schemas/primary-wallet-card-funding.ts`: trusted scope, immutable reservation, existing prefunded collection schema, existing normalized transfer schema, durable acknowledgements.
- `apps/web/src/lib/piggyvest/primary-wallet-card-funding-proof.ts`: checks collection identity, amount and customer email, then treasury-to-primary destination custody. Returns `collection_pending`, `custody_pending`, `reconciliation_required`, or token-free `ready_to_credit` evidence.
- `apps/web/src/lib/piggyvest/primary-wallet-card-funding-connection.ts`: loads the scoped stored reservation, verifies collection before custody, settles only matched evidence, exposes only status. `completed` requires `credited` or `duplicate` from the atomic ledger adapter.
- `apps/web/src/lib/piggyvest/primary-wallet-card-funding.types.ts`: dependency contract for trusted reservation storage, read-only verifiers and atomic settlement.

These files are not wired to routes, a controller, a database function or a provider worker. They do not initialize a checkout, charge a card, transfer money, migrate a balance or enable production. The dependency methods must be trusted server adapters; a parsed object or a callback from a browser is not authenticated financial evidence.

## Reuse and actual blockers

Existing `prefunded-card-checkout-provider.ts` already implements Paystack hosted card initialization and verification through `/transaction/initialize` and `/transaction/verify/:reference`. It restricts channels to card and checks reference, amount, NGN currency, test domain, customer email, metadata and reusable authorization before returning a verified collection. Authorization remains private; only persist it through the existing protected saved-method boundary after consent.

The provider cannot be directly invoked for a primary wallet: its intent requires `goalId`, `prefunded_first_card` metadata, a savings callback, a fixed system identifier and a reviewed deadline. Both allowed deadlines in `prefunded-card-known-deadline.ts` (September 29 and October 6, 2026) are expired as of October 7. Do not fabricate a goal, bypass expiry or renew configuration in this task. A parent change must extract the validated collection mechanics into a goal-independent adapter and separately review the primary-wallet consent, metadata and current staging configuration.

Existing `prefunded-card-provider.ts` has Paystack saved-authorization collection and PiggyVest staging `/api/v1/transfer/wallet` submission. Its transfer verification checks stored evidence or `collectPrefundedCardTransferProof`/`normalizePrefundedCardTransfer`, including ownership corroboration for the richer provider response. Those claims and ownership bindings are also goal-bound. Extract the primary-wallet ownership path using the actual primary mapping and provider identity crosswalk; never pass a primary wallet under a fake goal binding.

The new proof accepts only the existing normalized transfer shape containing business, source, destination, customer, amount, currency and transaction identity. For a rich `successful` response, the trusted parent verifier must first establish the existing crosswalk and authenticated source/destination wallet corroboration, then produce normalized evidence. Missing corroboration fails closed. Do not invent a PiggyVest card-charge endpoint or assume Paystack settlement is already in PiggyVest.

`prefunded-card-webhook-boundary.ts` currently returns retryable 503 for `pvb-first-` references or `prefunded_first_card` metadata. The new reservation deliberately uses that already protected reference family. A parent change must establish durable dedicated webhook intake before enabling collection; it must never allow these references to fall through to legacy top-up accounting.

## Concrete parent wiring

1. Keep `WalletFundPanel` card entry and its amount validation. In the existing `fundWallet`/controller parent, select PiggyVest primary funding using trusted merchant configuration. Route its request through a dedicated primary funding API adapter; preserve the legacy initializer for legacy merchants and recovery of already-created legacy payments. Do not silently fall back to legacy top-up when primary setup is incomplete. Show an actionable setup/readiness message while retaining the card action.
2. Authenticate first and validate CSRF/input in the parent API. Resolve merchant/customer ownership from the authenticated RLS client and trusted storefront context. The customer sends amount, consent and idempotency key, not integration ID, provider wallet, treasury, business or provider evidence. Load the primary mapping and enabled treasury binding server-side; reject absent or mismatched mappings before checkout. Use a restricted capability for durable funding operations, never a service-role client for the user request.
3. Atomically reserve a primary funding operation and treasury capacity before collection. Bind operation ID, intent ID, amount in integer kobo, environment, merchant/customer/integration, verified customer email, business, source treasury and primary destination/customer. Persist a request fingerprint and idempotency key, separate deterministic collection/transfer references, consent and lifecycle state. The new reservation has no savings goal. Repeating an idempotency key with changed amount or destination must conflict.
4. Adapt the existing card-only hosted checkout mechanics to that durable intent. Keep the `pvb-first-<intentId>` reference protection until dedicated webhook dispatch supports the primary intent explicitly. Bind primary metadata/fingerprint and use a primary-wallet return destination. Store the session before returning its checkout URL. Initialization ambiguity triggers verification of the same reference, not a fresh collection.
5. After a callback or signed Paystack event, enqueue/refresh the stored operation. Verify collection through the authenticated provider adapter. Persist verified collection and the saved authorization privately, mark `custody_pending`, create the durable treasury-transfer outbox record. Paystack success alone must neither increase spendable PiggyVest balance nor complete wallet funding.
6. A restricted worker sends the existing documented wallet transfer from prefunded PiggyVest treasury to the mapped primary wallet. Persist the submission claim and deterministic transfer reference before dispatch. An ambiguous result stays pending and is reconciled by that reference; never recharge the card or blindly resubmit the transfer. Verify provider transaction history/signed evidence and primary ownership before normalization.
7. Construct `createPrimaryWalletCardFundingConnection` with the trusted staging scope. Its `readReservation` adapter returns the stored immutable reservation for the supplied scoped operation ID; `verifyCollection` returns the existing verified/pending/reconciliation result; `verifyTransfer` returns authenticated normalized custody evidence or `null` while pending. `settleVerifiedCustody` applies the atomic transaction described below and returns only `credited`, `duplicate` or `conflict`.
8. Poll the scoped operation status after hosted checkout. Keep pending/reconciliation state visible and recover it on wallet reopen. Only durable completion refreshes the PiggyVest primary balance and dismisses funding. Preserve any interrupted purchase return destination using the existing allowlist. Provider balances, app-ledger credits and user-visible completion are separate evidence layers.

## Required durable ledger transaction

The settlement dependency is a required parent implementation, not an existing RPC name. It must lock the operation and re-read the immutable scope, amount, primary mapping and treasury reservation. It must verify that collection and custody evidence were recorded by trusted verifiers and that the operation is neither cancelled nor reversed. Do not accept proof JSON as authority from a customer-facing RPC.

Use unique claims on `(environment, integration, Paystack transaction ID)` and `(environment, integration, PiggyVest transfer transaction ID)` across all funding consumers, including legacy top-ups and savings. A transaction cannot back two operation IDs or two destinations. Atomically write the primary funding receipt, the treasury-capacity debit, the collection receivable and the primary ledger credit; mark completed and queue notification/cache invalidation in the same transaction. Amounts are integer kobo throughout. Replay with identical financial identity returns `duplicate`; replay with changed financial identity returns `conflict`. No amount-based or latest-balance deduplication.

If a PiggyVest signed inflow can describe this treasury transfer, both webhook intake and polling must consume the same provider transaction claim before crediting. The existing `primary-wallet-inflow-*` path handles bank-transfer receipts; do not manufacture a bank-transfer event for an internal wallet transfer. Coordinate the shared receipt claim and source classification in an append-only parent migration so neither event order creates a second credit.

Treasury funding is an advance backed by the verified Paystack collection. Paystack later settlement replenishes treasury only after actual documented settlement/bank evidence. A Paystack card success is not a PiggyVest treasury deposit. Failed collection, reversals or chargebacks need the existing reversal/reconciliation discipline and explicit recovery before releasing reservations. No automatic retry may issue a second charge. No refund completion may be inferred from failure or cancellation.

Preserve existing Paystack-funded legacy balances, transaction history and already-issued references. Do not relabel them as PiggyVest custody or bulk migrate their backing. Any aggregate display must preserve the backing split, and new Piggy-backed funding must use distinct durable source classification rather than `wallet_topup` legacy completion. Ordinary primary funds remain non-interest-bearing; savings transfers and interest require their separate opt-in plan flow.
