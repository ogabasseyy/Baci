# Primary permissions repair: local candidate only

This reuses the grant-before-revoke strategy from the existing staging `replay-app-public-grants.sql`; it does not reuse that installer's production-incompatible cluster binding or limited function selection. No deployed safety predicate or existing migration is modified.

`apps/web/tools/piggyvest-primary/repair-public-grants-local.sql` accepts explicit temporary manifests of reviewed objects and compatible consumer roles. Objects are pinned by OID, catalog-rendered identity, owner and exact prior ACL, including implicit PUBLIC function execution. It grants each existing PUBLIC privilege to the manifest consumers before removing that exact PUBLIC privilege. It does not discover additional targets, change schema usage, add memberships, change defaults or install authorities. Explicit existing grants are retained.

Restricted primary/staging role names and roles connected to them through either direction of membership cannot be preservation recipients. PostgreSQL's membership check includes SET ROLE paths, not just inherited access. An invalid recipient, unsupported object or ACL drift aborts the whole transaction. The script is deliberately guarded to a socket-connected `fixture_owner` session: it is not a production installer or an approved live manifest.

Local regression coverage uses separate disposable PostgreSQL instances with no TCP listener. It first reproduces the strict guard rejecting PUBLIC function, table and sequence privileges, including a function in an inaccessible schema. After repair, actual intake and worker SESSION_USER identities pass the unchanged guard. Existing INHERIT and NOINHERIT consumers keep the specified access. Direct function, table, sequence and inaccessible-schema privilege escalations still fail. An unrelated-name member of a restricted group is rejected as a consumer. ACL drift and forbidden recipients leave PUBLIC grants and prior ACLs intact after rollback. Future roles do not receive the historical grants implicitly.

Validation follow-up: four SQL integration files, seven tests pass, including genuine aggregate/window routines and routine-kind drift rollback. The candidate now pins expected_prokind and supports f/a/w only. The production-derived permissions-only clone and its ownership blocker are documented in `piggyvest-production-acl-rehearsal-20261023.md`. Neither rehearsal validates actual extension upgrade recreation or every application operation.

Monorepo lint and typecheck passed (six existing lint warnings). Independent review found that a combined privilege assertion could miss one lost permission; the regression now checks each table and sequence privilege separately, and all six tests passed again. The full repository suite was not rerun for this local SQL-only candidate; the previously documented clean-checkout gate remains separate.

Before any production proposal: freeze and independently review a complete production object/consumer manifest, inventory extension-managed objects and ownership limitations, rehearse that manifest on an isolated schema clone, and compare all required consumer privileges before/after. Future new roles require explicit grants; future PUBLIC grant recreation must fail readiness rather than be silently normalized. Do not run the staging installer against production or remove this candidate's local guard. A separately reviewed append-only deployment artifact is required. Live keys, services, balances, recording accounts, integration rows and authorities remain untouched.
