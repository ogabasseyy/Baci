# Baci ChatGPT Store Builder Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task. Use `superpowers:subagent-driven-development` only if the owner selects that execution method. Steps use checkbox (`- [ ]`) syntax for tracking. This document authorizes no implementation or external changes by itself.

**Goal:** Let authenticated Baci owners create, edit, preview and explicitly publish their websites from a new ChatGPT plugin, reusing Muse connector primitives and Baci's existing builder backend.

**Architecture:** A separate merchant MCP protocol adapter calls a fixed Baci HTTPS execution gateway in the existing Next.js Node runtime; that gateway resolves the linked user's normal Supabase RLS client and calls shared website services. OAuth links the account, a standard MCP Apps widget renders an editor-free shared Baci presentation, and an effect-bound owner approval protects publication and delivery verification. Existing Muse API and Ogabassey MCP contracts/deployments remain separate.

**Tech Stack:** Existing Node 24, pnpm/Turborepo, TypeScript, Zod, React/Puck, Supabase/PostgreSQL, Vitest/Testing Library/Playwright, Biome, SDK v2 MCP server/Node transport and MCP Apps UI; a maintained OAuth provider subject to Task 1 acceptance.

## Global Constraints

- Both existing submissions are protected: no cancellation, edit, resubmission, tool refresh or deployment to either submitted integration.
- Owner accounts first; an explicitly consented store is required. Preserve the current zero-or-one-owned-store account model and owner uniqueness constraint. IDs are selectors, not authorization. Staff access is denied in this plugin's v1; existing staff/browser permissions remain unchanged.
- Use `storefront.read`, `storefront.write`, `storefront.publish`; require read alongside write/publish. No service-role/admin client or Muse C-prime credential for new user-facing writes.
- Drafts live in separate owner/staff-authorized storage, never in a publicly readable published row. Task 0 must prove raw Data API privacy and legacy web/mobile compatibility; a client column list is not access control.
- Draft-first creation; established slugs immutable; semantic model input only; 64 KiB request bodies; instructions 1–4,000 characters; page size 1–20.
- Every mutation tool request requires an idempotency key; edit/application/publication require an exact opaque draft revision. Result retention is seven days; publication intents expire after ten minutes.
- Publication preserves current launch readiness and requires effect-bound Baci approval. No payment, KYC, domain-purchase or buyer-cart operations.
- Use the current locked compatible SDK family and existing component/AI validators. No new general PageSpec/CommerceRuntime framework or manual React memoization.
- Reuse AI computation, not the existing service-role job dispatcher. New builder operations and delivery retries run with normal linked-user RLS clients. Preserve both current published SEO/global settings and any separately pending private drafts. Homepage publication writes no `published_seo`, `published_store_settings` or `published_setup_settings`; do not advertise unimplemented mutations or call the existing broad publish helper unchanged.
- New stores reserve their canonical Baci subdomain and use explicit `template_id: 'puck'`. V1 edits, previews and publishes only `pageSlug: 'home'`; preserve secondary drafts and public routes. Existing template consumers must be proven compatible before edits/publication; no silent template migration.
- New migrations are append-only. `.env*`, `proxy.ts` and `business-types.ts` edits, environment provisioning and deployment require their exact owner authorization before execution.
- Plan baseline is `270fe355d8a78ddb685e3e490fcf6652fe89910e`. Recheck main and active worktree ownership before implementation; do not copy a dirty peer tree.

## Review Focus

1. Two chat/browser sessions edit the same site: one wins; the other receives `STALE_DRAFT`, with no lost live or draft data. Tasks 4 and 5.
2. An AI result arrives after revocation or after another edit: polling cannot apply it, and application fails closed. Tasks 3 and 5.
3. Publishing commits but eviction or the response fails: reconciliation reports the existing receipt and retries delivery, without publishing twice. Task 8.
4. A reconnecting new merchant already has an incomplete placeholder: provisioning completes exactly that owned record and never duplicates or exposes it. Task 4.
5. An approved intent is reused for another store, revision, destination or connection: no publication occurs. Task 8.

Use commit subjects specified below; no automatic push, merge or deploy. If the reviewer is unavailable, report that review gate as incomplete.
