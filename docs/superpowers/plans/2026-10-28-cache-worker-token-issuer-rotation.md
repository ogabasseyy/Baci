# Cache worker token issuer and rotation

## Status

Design only. This change adds no issuer, does not read or mint a production JWT,
does not alter any live GitHub/Vercel/Supabase secret, and does not deploy. The
current workflow still consumes the static
`secrets.CACHE_INVALIDATION_WORKER_TOKEN`; it must not be described as
short-lived or automatically rotated.

## Required security boundary

The cache route needs only the `cache_invalidation_worker` PostgREST role. Its
database grants remain the three cache outbox RPCs documented in
`vps-workers/docs/cache-invalidation-worker-capability.md`. The token must not
carry `service_role`, tenant/user identity, or any broader database capability.
The VPS retains only its existing `CRON_SECRET` request to the Next.js route.
Neither the Supabase JWT signing key nor its private key may be installed on the
VPS, copied into a Vercel environment, or made available to Vercel build or
runtime code.

## Issuer design

Use GitHub Actions as the issuer coordinator, on a GitHub-hosted runner only.
The issuer job must be pinned to the protected production environment and
`main`, use `contents: read` plus only the identity permissions required for
the selected signer, and never run repository-controlled untrusted code while
signing. Do not put issuance in the self-hosted `baci-release` job: it shares a
host with release infrastructure and is not the signing boundary.

Preferred signer: a dedicated asymmetric signing key in an already approved
cloud KMS/HSM, with GitHub Actions OIDC federation. The cloud trust policy must
match the exact repository, protected environment, workflow identity, and
`refs/heads/main`; the KMS principal may invoke only the specific signing key
and algorithm. The private key remains non-exportable. The issuer builds a
minimal JWT payload (`role`, bounded `iat`, `nbf`, and `exp`) and asks KMS to
sign it. It must not mint JWTs for arbitrary roles or caller-selected claims.

Do not create a cloud identity or KMS key as part of this source change. First
verify that an approved KMS and OIDC trust policy already exist. If they do not,
keep the migration blocked and submit a separate infrastructure decision. A
GitHub environment secret containing the Supabase legacy JWT secret is a
possible fallback only after owner/security review; it is a long-lived project
signing key even when used from a GitHub-hosted runner, so this plan does not
authorize that fallback. If the project has moved to non-exportable Supabase
signing keys, do not extract or replace them to enable this worker; use a
supported signer integration or stop here.

The JWT is a temporary delivery artifact. The signing key is never sent to
Vercel. The issued JWT may be set as the sensitive Production
`CACHE_INVALIDATION_WORKER_TOKEN` variable because the current route reads it
from the function environment. Token lifetime is 24 hours, with issuance and
deployment at least every 6 hours. This yields three retries of headroom and
keeps an old deployment's token valid while a replacement rolls out. Do not
choose a token lifetime shorter than the expected build, prebuilt deployment,
alias verification, and rollback window.

## Current metadata findings (2026-10-28)

The production Baci project's read-only Supabase Management API signing-key
metadata shows an `ES256` key in use, an `ES256` standby key, multiple prior
ES256 keys, and one `HS256` key in `previously_used` state. The public JWKS
endpoint publishes three ES256 verification keys. This confirms that the
current project uses the asymmetric signing-key system; it does not show
whether the in-use ES256 key was generated by Supabase or imported from an
external signer. The Management API response has no key-provenance field.

The codebase has a separate `SUPABASE_AGENTIC_JWT_PRIVATE_JWK` server-side
signing path and expects ES256 private JWK material to mint short-lived
authenticated-role tokens. This is evidence that the app has used or is
designed to use a matching imported signing key, but the JWK's `kid` could not
be compared to the in-use key from read-only metadata. Do not assume this key
is the cache worker's valid signer or copy it into GitHub/VPS storage.

Read-only Cloud IAM inventory found no Cloud KMS keyrings or Workload Identity
Federation pools in either Baci-named Google Cloud project visible to the
current account. The active local `gcloud` project is Ekaette. Read-only Vercel
KMS issuer inventory was denied with HTTP 403 for the Baci team; no Vercel CLI
token or linked project metadata was available locally. Therefore there is no
evidence that the preferred external signer exists today. The plan is blocked
until the owner selects an approved signer and its trusted identity path.

For cost sizing only, Google Cloud lists software-protected EC key versions at
about US$0.06 per active key-version-month and cryptographic operations at
US$0.03 per 10,000 operations; Google IAM and Workload Identity Federation
have no additional per-identity charge. These figures exclude any organization
support costs and do not imply billing is enabled for a Baci project.

### Owner decision

Choose one path before further implementation:

1. **Keep blocked (recommended until key provenance is confirmed).** Have an
   owner with Supabase and Vercel access compare only the `kid` metadata of
   `SUPABASE_AGENTIC_JWT_PRIVATE_JWK` with the active ES256 key, then approve a
   signer boundary. No production authority changes are needed for that
   metadata check.
2. **Provision an external signer.** Authorize a separately reviewed Google
   Cloud KMS/WIF setup, including billing/API enablement and a proof that its
   signing key matches a Supabase-trusted key. If no matching private key is
   already held by an approved signer, this requires generating/importing a
   new key and a coordinated Supabase signing-key rotation; that is a distinct
   production change and is outside this plan.
3. **Approve a protected CI secret fallback.** Store a copy of the relevant
   signing private key only in a protected GitHub production environment and
   mint the narrow token on a GitHub-hosted runner. This keeps the key off the
   VPS/Vercel, but gives GitHub CI a project signing key capable of minting
   other roles. It requires explicit security/owner approval and exact key
   provenance; do not implement it implicitly.

No choice authorizes modifying signing keys, memberships, or secrets in this
task. The project-signing key and its lifecycle are a higher-impact boundary
than the worker JWT; treating a KMS setup as a routine detail would conceal
the needed production decision.

## Rotation sequence

1. A scheduled GitHub-hosted workflow (and the ordinary protected production
   release workflow) obtains signer authorization through GitHub OIDC, signs a
   fresh 24-hour worker JWT, and marks the token for redaction immediately.
2. It validates the token locally without printing it: expected algorithm and
   key id, exact role claim, required time claims, maximum lifetime, and no
   unexpected authority claims. Validate signature against the signer public
   key. Reject a lifetime outside the policy window.
3. The existing Vercel env synchronizer writes only the named sensitive
   Production variable, reads it back only to prove presence, and never emits
   its value. Run this on a GitHub-hosted job with the narrowly scoped Vercel
   credential; the VPS receives neither signer credentials nor JWT.
4. Build once and deploy the already-built artifact through the required
   prebuilt flow. Vercel environment changes do not change existing
   deployments, so updating the variable alone is not rotation. Promote only
   after the exact deployment's health/capability probe passes.
5. Confirm the current production alias serves the expected app SHA and that
   the cache capability probe succeeds. Retain the previous deployment and
   token validity for the full overlap window; do not revoke database role
   membership as a token-rotation mechanism.
6. If issuance, env sync, build, deploy, alias check, or capability probe
   fails, leave the previous deployment untouched and retry before the
   previous token expires. Alert with run ID, SHA, phase, and expiry metadata
   only. Escalate before the remaining validity falls below the documented
   recovery window; never fall back to printing or manually copying a token.

The rotation workflow must be serialized with production publication and use
the existing release lock. It must reuse the exact current production source
SHA and prebuilt release path; it must not deploy a stale checkout just to
refresh a secret. If the normal release lock cannot prove this source SHA and
deployment relationship, rotation stays blocked.

## Implementation gates

- Confirm signing-key mode and the exact supported Supabase JWT verification
  behavior for the configured project. Do not infer exportability from a
  working local token.
- Confirm the KMS/OIDC provider is already approved and identify its project,
  key id, IAM trust conditions, token audience, and invocation audit log.
- Add a pure issuer module with fixed claims and strict lifetime validation;
  tests must cover wrong role, malformed key response, unexpected claims,
  expired/not-yet-valid tokens, overlong lifetime, and output redaction.
- Add the scheduled workflow with protected environment, pinned actions,
  `permissions` at job scope, GitHub-hosted runner, concurrency matching the
  production release lock, and no event path that lets an untrusted fork sign.
- Update the env sync contract to accept only a freshly validated token and to
  keep all token bytes out of stdout, stderr, artifacts, caches, and summaries.
- Prove rotation in a non-production project first, including environment
  update, prebuilt deploy, alias verification, failed deploy recovery, and
  overlap expiry. Never use a production signing key for that rehearsal.
- Review the resulting workflow and IAM policy before enabling a production
  schedule. Deployment and production secret changes remain separate explicit
  release actions.

## Unresolved risks

- No evidence in this source tree establishes whether production uses legacy
  imported or Supabase-generated asymmetric signing-key material; read-only
  metadata confirms ES256 is currently in use and legacy HS256 is not.
- No approved KMS identity, key, or GitHub OIDC trust policy is identified in
  this change, and read-only Baci GCP inventory found no KMS keyrings or WIF
  pools. Until those exist and are reviewed, no automatic issuer can be
  implemented safely.
- Vercel Production env updates affect new deployments only; a failed alias
  promotion can leave both old and new deployments active with different
  token expiries. The overlap and rollback path must be verified before
  setting the token lifetime.
- A scheduled workflow is not a guarantee of timely execution. Alerting must
  use token-expiry metadata and leave a recovery window, and the ordinary
  release workflow should also refresh the token.
- Current deployment configuration may make the Vercel credential available
  only on the prebuilt runner. The approved credential placement and exact
  source SHA handoff to a GitHub-hosted issuer need confirmation before
  changing workflow topology.
