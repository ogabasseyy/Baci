## Fixture use and outstanding qualification

Load the JSON as a shared input for web tests and disposable SQL fixture adapters. The keys are symbolic and intentionally different from production identifiers. Allocate deterministic UUIDs in the adapter and use a mapped test value where a serialized-unit column has format constraints. Reset inventory for each case. Amounts are integer kobo and stock deltas are available units. The cases describe order totals after pricing. Tax, promo reconstruction and externally issued invoice policy require fixtures derived from the actual qualified route during implementation.

Core scenarios reference a base order scenario by `orderCaseId`. The adapter applies the specified inputs, executes the steps and checks the resulting state. For the last-unit race, clone the original order and confirmed hold with distinct order, line, original unit and capture IDs, then contend for the same replacement unit in separate sessions. Reconciliation scenarios use the referenced base order plus any `orderOverrides`. The [fixture contract tests](../../../supabase/tests/fixtures/paid-order-amendments/scenarios.test.mjs) check the input files and expected outcomes with `node --test supabase/tests/fixtures/paid-order-amendments/scenarios.test.mjs`. They are fixture validation. Task 2 still owns the API and SQL behavior tests.
