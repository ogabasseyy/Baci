## Dispositions

1. **Missing payment transaction — confirmed, corrected in migration 926.** The customer-scoped reservation and initialization-claim RPCs now persist a uniquely bound pending transaction in the same SQL transaction, before any provider request or authorization URL. Existing reference/order/merchant/amount/currency/type/status conflicts fail closed. The order remains unpaid. No new service-role client is added. `platform_fee = NULL` deliberately retains the existing settlement fee-calculation fallback rather than introducing a fee waiver.
2. **Missing merchant fulfillment metadata — confirmed, corrected in migration 924 and checkout helpers.** Verified merchant shipping/pickup rate identity and pickup details enter the signed atomic order request and are stamped before attachment commits. Missing or cross-merchant rate references fail closed. Provider quote flows are unchanged.
3. **Partial refunds block remaining fulfillment — confirmed limitation, unsafe suggested shortcut rejected.** A whole-order shipping/status/item update is not proof that refunded units are excluded. Removing the partial-refund hold would make those units shippable again. The hold remains; processed partial refunds now have a durable lifecycle review record. Quantity-aware fulfillment reconciliation and its operational release path remain a launch blocker for partial refunds, not a completed fix.
4. **Approved verification replay lacks capture evidence — confirmed, corrected in migration 926.** Completion persists only the validated reference, amount, currency, success status and paid timestamp, plus the gateway fee retained at capture. It does not store card authorization/PAN/BIN data or the raw provider response. Replayed conflicting fees are rejected; an unchanged replay does not alter settlement evidence.
5. **Processed full refunds leave orders paid/unpaid indefinitely — confirmed, corrected financial lifecycle with bounded inventory handling in migration 925.** Finish and reconciliation both trigger idempotent order/transaction refunded state and a lifecycle receipt. Proven unshipped reserved serialized stock can be released. Sold, dispatched, mixed/nonserialized or otherwise ambiguous inventory remains held with a durable review-required record; a refund is not proof of physical return. The operations workflow for those records remains a release gate.
6. **Prediscount expected total rejects REDVAULT drafts — confirmed, corrected.** The helper removes the stale expected-total assertion while supplying the authoritative discount. PostgreSQL still computes the actual total from the validated catalog/order inputs; the client does not determine the payable total.
7. **Usage caps unenforced — confirmed, corrected at redemption in migration 925.** A locked campaign row serializes approval counts, including normalized customer identity and historical usage. Both configured discount-code limits and explicit structured commercial limits apply. Missing/unstructured terms fail closed. No numerical cap or unlimited policy is chosen for the owner. Reaching a cap after capture does not approve fulfillment; the capture remains held for recovery.
8. **Unattached draft can reserve stock indefinitely — confirmed, corrected for new creation.** A single protected RPC verifies a signed request, creates the draft, binds the item-level proof and stamps fulfillment atomically. Attachment failures roll back the order, allocations and reservations. Idempotent retries recover committed responses. Direct customer execution of the old draft-only RPC is revoked. Existing legacy orphan drafts still require deployment preflight/recovery; this change does not invent a stock-release decision for historical payments.
