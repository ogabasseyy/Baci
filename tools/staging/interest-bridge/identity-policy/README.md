# Staging interest identity and inactive policy preparation

All implementation lives in this directory. It performs no policy insert,
mapping overwrite, wallet remap, transfer, drain, receipt replay or activation.
The fixed deadline is `2026-10-06T15:59:10Z`; principal remains 10,000 kobo.
Public checkout and the financial runtimes are outside this lane.

## Evidence and trust contract

`verify_policy_candidate.py` checks exact opaque strings without normalization.
It accepts one complete independently reviewed customer identity path:

1. An authenticated provider registration reconciliation maps the exact app
   customer to the API alias, and a documented or signed provider mapping binds
   that alias to the webhook UUID. This path requires the exact app customer as
   the registration third-party identifier; the staging probe identifier fails.
2. An immutable app-goal historical receipt, independently reconciled against
   the provider transaction, binds the webhook UUID and exact historical public
   wallet under the same business. A current authenticated provider GET for that
   exact business and public wallet supplies the API alias. This joins two
   authorities through the wallet; it does not require `id_customer` or a
   third-party identifier. A missing historical HMAC remains `unavailable` and
   requires AEAD-authenticated original storage plus provider reconciliation.

The current interest wallet must have the identical API alias, explicit
`interestEnabled=true`, a proven public/FAAS pair, and an existing enabled
app-goal binding to that exact public wallet in the pinned physical database.
The existing funded goal is permanently pinned to its original public wallet.
Customer ownership of another wallet requires a separate new goal and a properly
provisioned binding, outside this fixed-scope preparer. Even a newly supplied
snapshot cannot authorize reassignment of the funded goal's history.
Separate `wallet_eligibility` evidence must document that this exact
business/API-customer/public/FAAS wallet is eligible for customer interest under
the provider arrangement. An accrual-enabled flag is insufficient by itself.

An independent payout-routing artifact must explicitly name the webhook
customer, exact source wallet, its documented public or FAAS namespace and the
destination. Equality of source and destination is accepted only when present
in that reviewed artifact. No source/destination equality is inferred.

Owner-authenticated opt-in must bind the exact merchant/customer/goal/wallet and
policy reference. A separately reviewed owner/provider contract attestation must
confirm 900 customer annual basis points and 300 business annual basis points.
The customer payout is already net: `full_customer_net_no_resplit` prevents a
second 9/12 split. The supplied gross 814, tax 81, net 733 fixture belongs only
in disposable PostgreSQL tests; this directory never credits it. Accrual remains
unspendable. Global rates alone do not prove individual wallet eligibility.

The evidence schema is `policy_contract.py`. All fields are required and extra
fields, bodies and credentials are refused. Each sanitized projection needs an
independent owner-reviewed registry entry:

```json
{"artifact-id":{"kind":"historical_receipt","sha256":"<64 lowercase hex>"}}
```

The hash is SHA-256 of `json.dumps(record, sort_keys=True,
separators=(',', ':'), allow_nan=False).encode()`. The registry is a trust input,
not proof generated by the verifier. The owner must authenticate the original
source and verify every projected relation before registering its pin. Do not
derive approval automatically from the candidate bundle itself. Both inputs
must be private, caller-owned, single-link regular files; symlinks, duplicate
JSON keys, nonfinite values and oversized files are refused.

Prepared output matches the installed policy columns and always has
`enabled=false`, `liveWritesAllowed=false`, `providerIdMappingApproved=false`.
The idempotency key hashes the exact policy and complete evidence closure.
Identical preparation reuses the existing artifact without changing its inode,
mtime or bytes. A different artifact at the output path is refused intact.
The live application must independently recheck the exact current identities,
deadline and bindings under transaction locks before any owner-approved write.
This offline result confers no live write authority.

## Parent root read-only procedure

Stage this directory as a fresh root-owned private bundle and verify its
`SOURCE-SHA256SUMS`. The parent runs the following once from that staged bundle:

```sh
/usr/bin/python3 -B collect_identity_evidence.py \
  --history /home/bassey/baci-legacy-proof-final.4flGg4nk/legacy-proof.json \
  --output /root/interest-identity-evidence-20261002.json
```

The historical source is pinned to
`86d683c4aab907efa1040baa41cfcc5e9efe21d5e427c2bb3f8e4a250a68db9c`.
Alternatively, use the applied root audit proof at
`/root/baci-legacy-migration.wUqQX5Rh/runtime/legacy-proof.json` with
`--history-sha256` set to its independently inspected exact file digest. Only
these two source paths are accepted; they are historical evidence, not renewed
replay authorization.
The collector accepts only that original report, reads the existing staging-only
root-owned 0600 treasury credential configuration through the existing pinned
`provider_interest_check.py` helper (SHA-256
`900b18bc7b25823a8ea36a663ee856a64eb8d37511502b45a3d5d9659ba365b1`).
It retains that helper's exact configuration digest and scope checks, staging
origin, certificate validation, redirect refusal and required User-Agent
`Baci-Staging-ReadOnly/1.0`. It does not read the intake credential file.
It GETs the old public wallet and known empty enabled wallet, then searches a
complete wallet-filtered transaction list, at most four 100-row pages, for exact
`PVB01M3CR6SZGH4K3GCPEMYKXYJ04`. The list URI is
`/api/v1/transaction?wallet_id=<old-public-wallet>&limit=100&collapse_batch=0`,
with bounded cursor pagination, as used by the pinned live helper and confirmed
in the [official list contract](https://www.piggyvest.business/docs/api/transactions).
No unverified single-transaction URI is attempted. It then runs
the literal `READ_ONLY_SQL` in `collect_identity_evidence.py` against the existing
isolated application database. It uses a repeatable-read read-only transaction,
a 10-second statement timeout and ROLLBACK. It reads the physical database
identifier and exact goal/customer/merchant/mapping/ledger binding. No receipt
claim, locks, grants or durable database writes occur. This is the exact needed
root query; no broader console investigation is necessary for this join.
The container psql path was independently observed as
`/nix/var/nix/profiles/default/bin/psql`, PostgreSQL 17.6; the presumed
`/usr/lib/postgresql/17/bin/psql` path is absent in this container. Bassey is UID
1001, confirmed by read-only SSH. The pinned helper source accepts UID 1001 or
root and refuses mutable or altered source bytes; its treasury configuration
must still pass root UID, mode 0600, single-link and exact digest checks.

Only sanitized identity projections enter the private output. Credentials,
provider bodies and subprocess errors are never printed. The CLI emits only
`collected_unreviewed` or a redacted refusal, with mapping approval false. The
historical signature status and `historicalObservedAt` are preserved. A fresh
transaction list GET must match the existing provider ID, successful credit,
exact wallet under the authenticated business and 10,000-kobo bank inflow.
The fresh list proves identity and amount; it does not claim to freshly verify
an absent fee or reference field. The original reconciled report supplies that
historical evidence. The fresh list supplies a separate
`providerRetrievedAt` and response digest. Historical observations are never
retimed as new provider evidence. Failed/ambiguous joins refuse output.
An existing output path is never overwritten. No root collector has been run
by this lane.

The parent can authenticate/review the four collected projections and supply
their pins. This establishes a potential customer join but still needs exact
wallet eligibility, payout routing, owner opt-in and the global split attestation. The observed
goal remains mapped to the disabled old wallet, so preparation additionally
refuses `goal_wallet_exact_link_missing` and
`new_goal_and_provisioned_binding_required` for the empty enabled wallet. Test
that wallet through a separate new goal with a provisioned binding; do not
change the funded goal's binding or reassign its history.

Run preparation with private reviewed inputs:

```sh
pnpm exec python3 -B tools/staging/interest-bridge/identity-policy/prepare_policy_candidate.py \
  --bundle /private/identity-bundle.json \
  --reviewed-pins /private/owner-reviewed-pins.json \
  --output /private/inactive-interest-policy.json
```

Exit 0 means an inactive candidate; exit 2 means a machine-readable evidence
refusal artifact; exit 1 means input or artifact preparation was refused.
